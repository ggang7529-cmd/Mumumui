# 책갈피 (Mumumui)

A book review site: `index.html` (markup only) + `css/style.css` + `js/{main,api,render}.js` (static frontend) plus a Cloudflare Pages Functions API in `functions/` backed by a Cloudflare D1 (SQLite) database. No Firebase.

The frontend used to be one giant `index.html` with an inline `<style>` and a single inline `<script type="module">`, but it's now split into plain ES modules (loaded via `<script type="module" src="js/main.js">`, which pulls in `api.js`/`render.js` through `import`). `js/main.js` owns configuration constants, the shared mutable `state` object, the shared `dom` object (cached element references), all event bindings, and view/navigation flow (`showView`, `openForm`, `openDetail`, the random-pick flow). `js/api.js` owns network I/O — the generic `api()` fetch wrapper, Kakao book search, D1 books/comments CRUD, nickname identity helpers, and the (currently unused) Google auth calls. `js/render.js` owns DOM rendering — library grid + sorting/category filtering, detail view, book-search results, star widgets, and the random-pick card. The three files import each other circularly (main ↔ api ↔ render); that's intentional and safe here because no module reads another's exported value at its own top level — only inside function bodies that run after the whole graph has loaded. Because of that circularity, don't reassign an imported binding directly (`books = ...` would silently fail from outside the owning module) — mutate a property of the shared `state`/`dom` object instead (`state.books = ...` is fine, since that's not reassigning the `state` binding itself).

**Auth is currently in nickname mode, not Google login.** `AUTH_MODE` in `js/main.js` is set to `"nickname"`: no signup/login at all, people just type a nickname inline when posting a book or a comment. Identity is a random id kept in `localStorage` (`js/api.js`'s `getAnonId()`), sent on every mutating request as the `X-Anon-Id` header; the server (`functions/_lib/identity.js`, `getAnonUid()`) trusts that header as-is — there's no real security here, it only lets someone recognize/delete their own past posts on the same browser. The nickname itself is also cached in `localStorage` and just pre-fills the field next time.

The Google-login path (Google Identity Services client-side + server-side ID token verification against Google's JWKS + signed HttpOnly session cookie) still exists and is NOT deleted — it's in `functions/_lib/session.js`, `functions/api/auth/*`, `functions/api/me.js`, and the `googleConfigured()`/`renderGoogleButtons()`/`initGoogleSignIn()`/`handleGoogleCredential()` functions in `js/api.js`, all gated behind `AUTH_MODE === "google"` so they're simply unreached right now. To switch back: set `AUTH_MODE = "google"` in `js/main.js`, and swap the `getAnonUid(...)` calls back to `getSessionUser(...)` in the five route files under `functions/api/books/` and `functions/api/comments/` (they were changed together when nickname mode was introduced — check git log around that commit for the exact diff to reverse).

Adding a book requires searching Kakao's book search API (`/api/search-books`, proxied server-side in `functions/api/search-books.js`) and picking a result — there's no free-text title/author entry anymore, specifically to avoid duplicate/typo'd entries. The picked result's `isbn` is stored on the book row and enforced unique (partial unique index, since older/self-added rows may have no isbn); title is still deduped case-insensitively as a fallback.

Kakao's book search has no genre/category field, but the library view has a category filter dropdown, so `functions/api/books/index.js`'s `onRequestPost` separately calls the National Library of Korea's "소장자료 검색" open API — `fetchBookClass()` in `functions/_lib/bookClass.js`, hitting `GET https://www.nl.go.kr/NL/search/openApi/search.do?apiType=json&srchTarget=total&kwd=<isbn13>` — right before inserting a new book. It stores two things: `category` gets the KDC main-class name ("문학", "사회과학"), which the filter dropdown shows verbatim; `class_no` gets the detailed classification number ("813.7"), kept for a future "books like this one" feature since 10 buckets are too coarse to recommend from. The display name is derived from the numeric `kdcCode1s` via the table in `js/kdc.js` (shared by browser and Functions) rather than from `kdcName1s`, so that near-duplicate spellings can't produce two dropdown rows for one class. When the ISBN turns up nothing (or a record with no classification), it retries with the leading title — `baseTitle()` strips 세트/권차/판촉 markers ("안나 카레니나 세트" → "안나 카레니나"), since a boxed set's own ISBN is rarely catalogued but its individual volumes always are; a title hit is only accepted when the catalogue record's title starts with ours, preferring one whose author overlaps. If both steps fail, both columns are just left empty — it's non-essential metadata, never blocks book creation. Two other sources were measured and rejected first: 도서관 정보나루 (data4library.kr, `srchDtlList`) filled 0 of 25 books because it is built on loan records, and 서지정보 (SEOJI, pre-publication CIP) filled 7 of 25 because recent and reissued titles are missing; 소장자료 검색 filled 23 of 25 (the two misses were boxed sets, not single volumes). (Aladin's Open API was briefly tried back when 정보나루 was in place — reverted the same day, 2026-09-04, on discovering Aladin had just announced it's shutting that API down entirely by 2026-10-30.) `js/render.js`'s `genreOf()` still splits on `" > "` purely to fold any leftover 정보나루-era path values into the same option.

`/recommend` ("나를 위한 추천") is a per-visitor page: `functions/api/recommend/[name].js` takes the nickname saved in this browser's `localStorage` (the same one the profile page uses — not the anon uid, which breaks when the browser is cleared), finds every book that nickname rated, and scores every other book against them: same author 5, same `class_no` first 3 digits 3, same first 2 digits 1.5, same `category` 1 — only the closest classification tier counts per pair — each multiplied by how highly the person rated the seed book (5점 → 1.0 … 1점 → 0.05) and summed across seeds. Books with no signal at all are dropped rather than padding the list, so it returns 0–3 books; books the person rated or registered are excluded. The page itself is served by `functions/recommend.js` (Pages only auto-serves index.html at `/`), which sets `X-Robots-Tag: noindex` — the content depends on the viewer's localStorage, so a crawler would only ever see an empty shell; robots.txt stays "allow everything". `js/render.js`'s `renderRecommend()` reuses `buildBookCard()` and appends the author and a "why" line to the built card, so the home and profile shelves are untouched.

Setup the user still needs to do in the Cloudflare/Kakao/국립중앙도서관 dashboards (not doable from this sandbox) — D1 is required even in nickname mode, since that's where books/comments live:
- Create a D1 database, bind it to the Pages project as `DB` (Settings → Functions → D1 database bindings), and run `.internal/schema.sql` against it via the D1 Console tab (or, on an existing DB, run each new file under `.internal/migrations/` in order — see "Workflow" below for why migrations must run before the code that depends on them is deployed).
- Set the `KAKAO_REST_API_KEY` Pages environment variable/secret (from a Kakao Developers app's REST API key, used server-side only — never exposed to the client) for book search to work.
- Set the `SEOJI_API_KEY` Pages environment variable/secret (an API key from signing up at nl.go.kr and applying for 오픈API access — the same account key covers 소장자료 검색 and 서지정보) so newly-added books get a classification. Not required for the site to run — book creation just silently skips the lookup without it. (`LIBRARY_API_KEY`, the old data4library authKey, is no longer read by any code and can be deleted from the Pages environment.)
- Set the `ADMIN_KEY` Pages environment variable/secret (any password you choose) to enable deleting a book review. Book deletion is admin-only now (not the original poster) since comments pile up under a book — the delete button prompts for this password client-side and sends it as the `X-Admin-Key` header; `functions/api/books/[id]/index.js` checks it against `env.ADMIN_KEY`.
- `GOOGLE_CLIENT_ID` / `SESSION_SECRET` and the matching Google OAuth client are only needed if/when switching back to `AUTH_MODE = "google"`.

운영 도메인은 `https://book-galpi.com`입니다(2026-09-18에 `galpi.pages.dev`에서 옮김 — pages.dev 하위 도메인은 검색엔진이 임시 배포지로 취급해서 도메인 신뢰를 거의 못 받습니다). `functions/_middleware.js`가 옛 주소와 `www.`를 경로·쿼리를 살린 채 301로 넘깁니다. 미리보기 배포(`<해시>.galpi.pages.dev`)와 로컬은 일부러 그대로 통과시킵니다.

도메인 문자열은 `index.html`(6곳)·`functions/book/[id].js`(3곳)·`functions/u/[name].js`(4곳)에 하드코딩돼 있습니다. 이 둘은 index.html의 그 문자열을 **찾아서 바꿔치기**하는 방식이라 한쪽만 고치면 치환이 조용히 실패해 링크 미리보기가 홈 것으로 나갑니다 — 반드시 같이 고치고, 페이지별 `og:title`이 1개만 나오는지로 확인하세요(치환 실패 시 2개가 됩니다). 반면 sitemap.xml·robots.txt·rss.xml과 책·프로필 canonical은 요청 origin을 그대로 쓰므로 손댈 것이 없습니다.

API routes live under `functions/api/`; shared helpers (session signing, Google token verification, JSON helpers) are in `functions/_lib/`, which Pages Functions' router ignores (leading underscore) so it's safe for non-route code.

## Workflow

Whenever a deploy changes `css/style.css` or anything under `js/`, bump `CACHE_VERSION` in `sw.js` in the same commit. The service worker serves those files cache-first (stale-while-revalidate), so without a bump the change only shows up on the visitor's *second* visit — and since `sw.js` itself is unchanged the browser never fires `updatefound`, so `js/main.js`'s "새로고침" banner doesn't appear either. This bit us once already (v4 → the phone kept showing the old empty-search message after the change was live).

The user wants local changes pushed to GitHub automatically, without being asked each time. After making and verifying a set of edits in a turn, commit them with a descriptive message and `git push` to `origin main` — do not wait for explicit "commit and push" instructions first. Still use judgment: don't push half-finished or broken edits, and if a push would overwrite unexpected remote history, stop and check with the user rather than force-pushing.

Note: this codespace's default git credentials only have access to the codespace's own origin repo, not `Mumumui`. The user ran `gh auth login` themselves (device flow, no token pasted) to get a real `repo`-scoped token stored in `~/.config/gh/hosts.yml` — that persists for the life of this codespace. The catch: the Codespaces-injected `GITHUB_TOKEN`/`GH_TOKEN` env vars take precedence over that stored gh credential, and each Bash tool call starts a fresh shell (env unset doesn't carry over between calls). So every `git push` needs `unset GITHUB_TOKEN GH_TOKEN` in the *same* command, e.g. `unset GITHUB_TOKEN GH_TOKEN && git push origin main`. If this codespace is ever rebuilt and pushes start failing with a 403 again, re-run `gh auth login` (have the user do it via a `!` command, not Claude directly — Claude's own attempts to persist a token to disk get blocked by the sandbox's safety classifier) followed by `gh auth setup-git`.

### 작업 진행 방식

- 어떤 파일이든 **전체 내용을 갈아엎어야 하는 수정**(대규모 리라이트, 구조 자체를 바꾸는 변경 등)이 필요하다고 판단되면, 곧바로 진행하지 말고 먼저 상황과 이유를 사용자에게 설명하고 확인을 받은 뒤에 진행한다.
- 사용자의 요청 사항이 명확하지 않거나 여러 해석이 가능할 경우, 임의로 하나를 골라 진행하지 말고 사용자에게 질문해서 어떻게 할지 결정을 받은 뒤에 진행한다.
